# Architecture notes

## Request flow
React page → TanStack Query → `api/endpoints.ts` → FastAPI route (auth + permission + schema validation) → service (rules, one transaction) → SQLAlchemy models → DB.
Audit rows and notifications are added to the same session as the business change and committed together.

## Core invariants and how they are enforced
| Invariant | Mechanism |
|---|---|
| One active patient per bed / one active bed per patient | partial unique indexes on `bed_assignments` (`released_at IS NULL`) + service pre-checks |
| Unavailable beds cannot be assigned | `assign_in_txn` requires `status == available` |
| No negative stock | `CHECK quantity >= 0` + guarded atomic UPDATE |
| One open transfer / discharge per patient | partial unique indexes on `transfers`, `discharges` |
| Valid state transitions | `TRANSITIONS` tables in `transfer_service` / `discharge_service` |
| Atomic transfer / discharge completion | single transaction; any failure rolls back everything |
| No duplicate active alerts | partial unique index on `notifications.dedup_key` where unresolved |
| Idempotent events | unique `notifications.event_key` |
| No PHI in notifications/audit | internal patient codes only; audit stores field *names*, and blocks PII keys |

## Alert logic
* Stock: `qty <= critical_threshold` → critical; `qty <= min_threshold` → low (warning); otherwise recovered (open alerts auto-resolved, success notification).
* Occupancy (per department, excluding maintenance/unavailable beds): `>= occupancy_warning_pct` → warning, `>= occupancy_critical_pct` → critical; thresholds are database settings.

## Routing score
Eligible departments (open, free beds not already claimed by pending transfers, under capacity, resource rules satisfied) are scored
`100 × (w_avail × free/operational + w_occ × (1 − occupancy))`, ×0.8 if the department is in `limited` status. Every candidate returns reasons and blockers. Weights are settings.

## Known limitations
Department staff are not scoped to their own department; no login rate limiting; the initial Alembic revision builds from model metadata (later revisions should be autogenerated); notification read-state is shared across staff, not per user; MCP/A2A not implemented.
